02 / Verification layers

Each layer answers its own question

No single document proves the entire chain. Select a layer to see its trust boundary.

What it proves

The runtime SBOM inventories published files, while a separate build SBOM describes build tools and dependencies. Formats: SPDX and CycloneDX.

Trust boundary

An SBOM does not prove that production was built from the stated repository or serves this artifact at all.

What it proves

Which known vulnerabilities Grype matched against the runtime and build SBOMs at scan time, recording the exact database version.

Trust boundary

Zero matches does not mean zero vulnerabilities. Errors or an unavailable database are never reported as a clean result.

What it proves

Which workflow built the artifact with this digest, from which commit, and using which input materials.

Trust boundary

Provenance requires signature verification and trust in the declared CI identity; raw JSON is not authentic on its own.

What it proves

An independent rebuild from the same declared inputs produces the exact same artifact byte for byte.

Trust boundary

A match confirms the build procedure, but does not by itself tell you which artifact is deployed.

What it proves

The payload was signed by the expected GitHub workflow via a short-lived OIDC identity and has not been altered.

Trust boundary

A signature authenticates the digest and statement, not the truthfulness of every claim inside them.

What it proves

Which exact HTML, JavaScript, CSS, and Worker source files belong to a single signed release.

Trust boundary

The manifest declares expected bytes. Live production responses still have to be fetched and compared separately.

What it proves

An independent process checked the identity, all linked digests, and live production responses; both the exact JSON and human-readable report are stored in a signed immutable verification release.

Trust boundary

The result applies to the stated release at verification time; a runtime compromise afterward requires a fresh run.

What it proves

Standard Subresource Integrity checks the entry script and stylesheet. importmap.integrity pins SHA-384 for every JS module, including transitive imports, while CSP pins the hash of the import map itself.

Trust boundary

SRI does not protect the HTML document that carries the expected hash—that is checked by the external verifier. CSS loaded via @import or url() requires separate controls.

Verified by CI: Cosign signatures, provenance, SBOMs, CVE scan, and reproducible build. Verified now in your browser: current deployment identity, SHA-256 of all production files, SHA-384 Subresource Integrity, and complete importmap.integrity for JavaScript modules.

The online verifier fetches production files directly and never executes code from the target site. For a full local verification of signatures and the rebuild, run the command on the right.
